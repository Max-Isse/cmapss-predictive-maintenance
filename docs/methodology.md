# Methodology

Sections 1–2 cover the data and the features (phase 3); models, uncertainty and the decision layer follow in
phases 5–6. Evidence for every number below: [reports/features.md](../reports/features.md) (generated by
`cmapss gold`). Decisions: [decisions.md](decisions.md).

## 1. Data, unit of analysis and targets

- **Data.** NASA C-MAPSS FD001–FD004: simulated turbofan engines, one row per engine per operating cycle, three
  operating settings and 21 sensors. Training engines run until failure; test engines stop at an unknown point and
  NASA gives their true RUL at the last observed cycle. It is a simulation (see `data/README.md`): results describe
  this benchmark, not a real fleet.
- **Unit of analysis.** Engine × cycle in gold. A prediction is made at a cycle using that engine's history up to
  and including that cycle. Engines, not rows, are the independent units: splits and cross-validation group by
  engine (phase 5).
- **Regression target.** Remaining useful life `rul`, capped at 125 (`rul_capped`, piecewise linear; D-016).
  Above roughly 150–170 cycles before failure the sensors show no wear, so the uncapped target asks the model to
  predict something the data cannot show; the cap turns that into "healthy" and concentrates the fit on the
  degrading phase that matters for maintenance. Evaluation also reports the uncapped `rul`.
- **Classification target.** `fail_within_n` = 1 when `rul ≤ N`, with N = 30 cycles, the assumed maintenance
  lead time (D-017). It is the probability the decision layer uses.
- **Assumptions checked.** Engine cycles run 1..n without gaps (silver rule, D-011; none found). Test RUL covers
  every test engine (silver check). Six discrete operating conditions (every point within 0.005 standardised
  units of a centroid).
- **Where this can fail.** Two fault modes in FD003/FD004 move some sensors in opposite directions; a model
  assuming one direction per sensor would be wrong there. The RUL cap biases predictions for genuinely young
  engines towards 125 by design.

## 2. Features

All feature constants are fitted on training engines only and saved as a versioned spec; one function
(`features/build.py::build_features`) computes features for training, the replay and serving (D-013).

1. **Operating condition** (D-014): k-means (k = 6) on standardised settings, best of 10 seeds; each row gets the
   nearest centroid and the distance to it.
2. **Near-constant sensors removed** (D-013): sensors with at most 2 distinct values within every condition carry
   the condition, not health: 01, 05, 16, 18, 19 dropped; 16 kept sensors.
3. **Per-condition normalisation** (D-015): z-score each kept sensor with its condition's training mean and
   standard deviation. In FD002/FD004 this lifts the correlation of the strongest sensors with RUL from about 0 to
   −0.65…−0.69.
4. **Rolling statistics** (D-015): mean, standard deviation (PySpark window functions) and least-squares slope
   (Spark SQL `regr_slope`) of each normalised sensor over the last 5, 15 and 30 cycles; plus the cycle number.
   161 feature columns.
5. **Point-in-time correctness.** Windows are `RANGE BETWEEN w−1 PRECEDING AND CURRENT ROW` within the engine,
   and the spec constants are fitted once on the training set as a whole, like any scaler; test, replayed and
   served engines never contribute to them. (Training rows therefore see condition statistics that include later
   cycles of training engines: a standard fit-on-train effect with 8,000+ rows per condition, and the test set is
   unaffected.) Tested two
   ways: unit tests replace the future with garbage or cut it off and require identical features
   (`tests/test_features.py`), and every `cmapss gold` run recomputes features for all 1,416 engines cut at a
   random cycle and requires an exact match (134,007 rows, maximum difference 0).

**Not done, and why.** No smoothing filters (exponential or Savitzky–Golay) beyond rolling means: the window means
and slopes already reduce noise, and fewer feature families keep the model card readable. No condition-history
features (cycles spent in each condition): the per-condition normalisation removes the condition effect on each
reading; this can be revisited if FD002/FD004 errors are much higher than FD001's in phase 5.
